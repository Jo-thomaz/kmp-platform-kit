# Prompt — Build the Reusable KMP Scaffold (Phase 0)

Goal: a project-agnostic template repo that any future app starts from, plus the machine-readable
knowledge the harness needs to develop features in it automatically.
Keep `token-efficiency-rules.md` loaded as the standing rules.

---

## Constraints
- Development machine: Windows/Linux with Android Studio. No local Mac.
  - iOS code must still be written and kept compilable; it is verified on a macOS CI runner, not locally.
  - Never claim iOS code works without a passing macOS CI job.
- Kotlin Multiplatform shared core. Native UIs: SwiftUI (iOS), Jetpack Compose (Android).
- Everything project-specific (app name, package/bundle id, brand tokens) comes from ONE config file. No hardcoded names anywhere else.

## Repository layout
```
scaffold.yaml                 # project config: name, packageId, bundleId, minSdk, iOS target, features
architecture.yaml             # machine-readable rules the harness reads (layers, allowed deps, naming)
build-logic/                  # Gradle convention plugins (kmp-library, android-app, feature, testing)
gradle/libs.versions.toml     # single version catalog
design-tokens/
  tokens.json                 # SINGLE source of truth (W3C DTCG format): color, typography, spacing, radius, elevation, motion
  build/                      # generator config (Style Dictionary or a small Go/Kotlin generator)
shared/
  core/                       # result types, errors, dispatchers, logging, ids (UUIDv7)
  data/                       # ports + adapters (Ktor remote now; local adapter slot for later)
  domain/                     # pure Kotlin, no framework imports
  feature/reference/          # golden reference feature: UiState, Action, presenter, tests
  umbrella/                   # the single framework exported to iOS (SKIE configured)
androidApp/
  designsystem/               # generated Compose tokens + Material theme mapping + base components
  feature/reference/          # golden reference Compose screen + screenshot tests
iosApp/
  DesignSystem/               # generated Swift tokens + base SwiftUI components
  Features/Reference/         # golden reference SwiftUI screen + snapshot tests
docs/
  ARCHITECTURE.md             # human version of architecture.yaml
  REPO_MAP.md                 # generated module → class → signature index
  playbooks/                  # step-by-step recipes the harness follows
    add-feature.md
    add-screen.md
    add-token.md
    add-api-endpoint.md
  parity/MATRIX.md
.github/workflows/
  shared-and-android.yml      # Linux: commonTest, Android build, screenshot tests, Konsist, detekt
  ios.yml                     # macOS runner: framework build, xcodebuild test, snapshot tests
```

## Design tokens
- One `tokens.json` generates both outputs. Never hand-edit generated files.
  - Android: Kotlin objects + a `CompositionLocal`-based theme, mapped onto Material 3.
  - iOS: Swift `Color`/`Font`/`CGFloat` extensions + an environment-based theme.
- Two layers: primitive tokens (raw palette, scale) and semantic tokens (`color.background.surface`, `color.text.primary`). UI code may only use semantic tokens.
- Light and dark modes in the token file.
- CI check: generated files are up to date with `tokens.json` (fail if regeneration produces a diff).
- Lint rule: no raw hex colors, raw dp/pt values or hardcoded fonts in feature UI code.

## Shared core rules (also encode in architecture.yaml)
- All logic lives in `shared`. UIs render `UiState` and send `Action`s only.
- Dependency direction: feature → domain → core; data implements domain ports. Domain imports no Ktor, SQLDelight or platform APIs.
- Every feature presenter exposes `StateFlow<UiState>` and `onAction(Action)`.
- Typed errors (`DomainError`), client-generated ids, idempotency keys on mutations.
- Enforce with Konsist tests that read the same rules as `architecture.yaml`.

## Harness knowledge (what makes automatic development possible)
- `architecture.yaml`: layers, allowed dependencies, naming conventions, file locations per artifact type.
- `docs/playbooks/*.md`: exact steps, file paths and gates for each task type.
- Golden reference feature on all three layers: the pattern the agent copies.
- `docs/REPO_MAP.md`: generated by a script, regenerated in CI.
- The harness must read these files; it must not rely on knowledge baked into prompts.

## Instantiation
- A generator command (Go CLI preferred: `scaffold new --config scaffold.yaml`) that creates a new project:
  replaces names/ids, regenerates tokens, removes the reference feature on request, initialises git.
- Record the scaffold version used in the new project (`.scaffold-version`) so upgrades can be applied later.

## Working method
1. Reply with a plan: module list, convention plugins, token pipeline choice, and CI jobs. Wait for approval.
2. Build in this order: build-logic + version catalog → shared core/domain/data → design tokens pipeline → reference feature (shared) → Android reference screen → iOS reference screen (compile-only locally) → CI workflows → playbooks + architecture.yaml → generator CLI.
3. After each step: files changed, gates run + result, open issues. Then wait.

## Definition of done
- `./gradlew check` passes on Linux (shared tests, Android build, screenshot tests, Konsist, detekt).
- The iOS workflow file exists and is ready to run on a macOS runner; local status reported honestly as "unverified until CI".
- `scaffold new` creates a fresh, building project with a different name and brand tokens.
- Playbooks are complete enough that the harness can run `add-feature` without extra instructions.
